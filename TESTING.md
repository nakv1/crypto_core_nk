# Проверка CryptoCore

## Проверка генератора через NIST STS

### Зачем

NIST Statistical Test Suite (STS) - набор из 15 статистических тестов.
С помощью него проверялись байты из `cryptocore.csprng.generate_random_bytes`.

Такая проверка помогает найти заметные статистические закономерности в случайных данных, но не доказывает криптографическую стойкость генератора.

### Окружение

- NIST STS 2.1.2;
- WSL 2;
- Ubuntu 24.04.5 LTS;
- исполняемый файл:

```text
/home/nak/nist-sts/sts-2.1.2/sts-2.1.2/assess
```

Отдельной документации README, PDF или DOC в установленной поставке STS не оказалось, поэтому параметры запуска были проверены по исходникам программы, в основном по `src/assess.c` и `src/utilities.c`.

### Данные

Файл со случайными данными создаётся скриптом проекта на Windows вне репозитория:

```powershell
python scripts/generate_sts_data.py C:\Users\nak\cryptocore_sts\cryptocore_sts_data.bin
```

Размер файла:

```text

80 000 000 бит
```

В WSL этот же файл доступен по пути:

```text

```

### Запуск

NIST STS запускался из его корневого каталога:

```bash
./assess 1000000
```

Число `1000000` означает длину одной проверяемой последовательности в битах.

Ответы на вопросы программы:

```text
0
/mnt/c/Users/nak/cryptocore_sts/cryptocore_sts_data.bin
1
0
80
1
```

По порядку это означает:

- читать данные из файла;
- использовать указанный путь;
- выбрать все 15 статистических тестов;
- оставить параметры тестов по умолчанию;
- обработать 80 последовательностей;
- использовать бинарный формат входных данных.

В результате файл размером 80 000 000 бит был разделён на 80 последовательностей по 1 000 000 бит.

Использовались стандартные параметры:

- Block Frequency: `M = 128`;
- Non-overlapping Template: `m = 9`;
- Overlapping Template: `m = 9`;
- Approximate Entropy: `m = 10`;
- Serial: `m = 16`;
- Linear Complexity: `M = 500`.

Перед запуском каталог результатов `experiments/AlgorithmTesting` не содержал старых файлов, поэтому результаты разных запусков не смешивались.

Итоговый отчёт STS находится здесь:

```text

```

Подробные результаты отдельных тестов находятся в каталогах:

```text
experiments/AlgorithmTesting/<TestName>/
```

Файл со случайными данными и полный набор результатов STS в Git не добавляются.

### Как читать итоговый отчёт

В отчёте STS используются два разных показателя.

1. **PROPORTION** показывает, сколько последовательностей прошли конкретный тест.

   Отдельная последовательность считается прошедшей, если её `p-value` не меньше `0.01`.

   В контексте STS ориентир из m3 `p-value >= 0.01` прежде всего относится к этому уровню.

2. **P-VALUE** в итоговом отчёте проверяет, насколько равномерно распределены p-value всех последовательностей.

   Для этого показателя STS использует другой порог:

```text
P-VALUE >= 0.0001
```

Минимальная допустимая доля прошедших последовательностей рассчитывается по формуле NIST SP 800-22:

```text
(0.99 - 3 * sqrt(0.99 * 0.01 / m)) * m
```

Для 80 последовательностей получается примерно:

```text
76.53
```

Для 52 последовательностей:

```text
49.33
```

В STS 2.1.2 рассчитанный порог хранится в переменной типа `int`, поэтому дробная часть отбрасывается. Фактически программа использует значения 76 и 49.

В итоговом отчёте это выглядит так:

```text
The minimum pass rate for each statistical test with the exception of the
random excursion (variant) test is approximately = 76 for a
sample size = 80 binary sequences.

The minimum pass rate for the random excursion (variant) test
is approximately = 49 for a sample size = 52 binary sequences.
```

Если строка не проходит один из критериев STS, программа помечает её символом `*`.

### P-VALUE ниже 0.01

У пяти строк из 188 значение `P-VALUE` оказалось ниже `0.01`.

Это не считается провалом STS, потому что для этого показателя используется порог `0.0001`.

Эти значения приведены отдельно:

- Non-overlapping Template, шаблон 34 (`001001011`): `0.006196`, `80/80`;
- Non-overlapping Template, шаблон 54 (`010000111`): `0.001859`, `79/80`;
- Non-overlapping Template, шаблон 138 (`111101010`): `0.006196`, `79/80`;
- Non-overlapping Template, шаблон 145 (`111111000`): `0.003577`, `77/80`;
- Random Excursions Variant, состояние `+1`: `0.002374`, `51/52`.

Все эти значения выше штатного порога STS `0.0001`.

### Random Excursions

Для Random Excursions и Random Excursions Variant использовались только 52 последовательности из 80.

Эти тесты работают только с последовательностями, в которых набралось достаточное число циклов случайного блуждания.

Для последовательности длиной 1 000 000 бит требуется не меньше 500 циклов. Этому условию соответствовали 52 последовательности.

Оставшиеся 28 последовательностей эти тесты не использовали. Само по себе это не считается отказом теста.

NIST SP 800-22 рекомендует использовать не менее 55 последовательностей для проверки равномерности p-value.

В данном запуске подходящих последовательностей было 52, поэтому значения `P-VALUE` для Random Excursions и Random Excursions Variant нужно оценивать с учётом этого ограничения.

Это относится в том числе к значению:

```text
0.002374
```

для состояния `+1` в Random Excursions Variant.

### Вывод

Все 15 тестов NIST STS были выполнены.

В итоговом отчёте нет строк со звёздочкой `*`, все 188 строк прошли критерии, которые использует STS.

Явных статистических проблем в данных, полученных через `cryptocore.csprng.generate_random_bytes`, тесты не обнаружили.

При этом один прогон NIST STS помогает выявить статистические проблемы, но не доказывает безопасность или криптографическую стойкость CSPRNG.

## Спринт 4: хеширование

### Корректность

SHA-256 и SHA3-256 проверяются по четырём контрольным векторам и известным ответам, используемым в тестах:

| Сообщение | SHA-256 | SHA3-256 |
|---|---|---|
| пустое | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` | `a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a` |
| `abc` | `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` | `3a985da74fe225b2045c172d6bd390bd855f086e3e9d525b46bfe24511431532` |
| `abcdbcdecdefdefgefghfghighijhijkijkljklmklmnlmnomnopnopq` | `248d6a61d20638b8e5c026930c3e6039a33ce45964ff2167f6ecedd419db06c1` | `41c0dba2a9d6240849100376a8235e2c82e1b9998a999e21db32dd97496d3376` |
| миллион символов `a` | `cdc76e5c9914fb9281a1c7e284d73e67f1809a48a497200e046d39ccc7112cd0` | `5c8875ae474a3634ba4fd55ec85bffd661f32aca75c6d699d0cdcb6c115891c1` |

Для SHA-256 отдельно проверяются длины 0, 1, 55, 56, 63, 64, 65, 119, 120 и 128 байт. Для SHA3-256 проверяются длины 0, 1, 134, 135, 136, 137, 271, 272 и 273 байта. Дополнительные детерминированные сообщения сравниваются с `hashlib`.

Потоковый интерфейс проверяется подачей одного сообщения целиком и частями разного размера. Тесты также подтверждают, что внутренний буфер хранит только неполный блок, повторный `digest()` не меняет состояние, а после него можно продолжить `update()`.

Лавинный эффект проверяется на шести заранее заданных сообщениях для обоих алгоритмов. В каждом сообщении меняется младший бит первого байта. Для каждой пары должно измениться строго больше 100 и строго меньше 156 бит результата. Среднее по шести парам должно находиться в диапазоне от 120 до 136 бит.

### Совместимость с внешними утилитами

SHA-256 сравнивался с `sha256sum` из GNU coreutils 8.32, установленным вместе с Git for Windows.

Для SHA3-256 в m4 указана команда `sha3sum -a 256`. В использованном окружении `sha3sum` не найден, поэтому для проверки применялся OpenSSL 3.2.1:

```text
openssl dgst -sha3-256
```

Это отклонение от TEST-3 в m4. OpenSSL выступает независимой реализацией SHA3-256. Если задана переменная `CRYPTOCORE_SHA3SUM` или совместимый `sha3sum` найден в `PATH`, автоматический тест использует `sha3sum`; иначе выбирается OpenSSL.

Проверяются пустой файл, короткий текст, набор всех байтов от `0x00` до `0xff` и детерминированные данные длиной 4097 байт. Из вывода CryptoCore и внешней утилиты извлекается только 64-символьное значение хеша, потому что текстовый формат строк у программ различается.

### Сборка пакета

Wheel собирался из чистой копии, полученной через `git archive HEAD`:

```powershell
python -m pip wheel <копия> --no-deps -w <каталог>
```

Сборка выполнялась с изоляцией. В `.venv` нет `setuptools`, поэтому `pip` установил его во временное окружение сборки. `.venv` и `pyproject.toml` не менялись.

В wheel присутствуют `cryptocore/hash/__init__.py`, `cryptocore/hash/sha256.py`, `cryptocore/hash/sha3_256.py`, `cryptocore/csprng.py` и прежние модули AES, режимов и padding. Точка входа в `entry_points.txt`:

```text

```

### Файл больше 1 ГиБ

Тест `tests/test_large_file_hash.py` включается только при `CRYPTOCORE_RUN_LARGE_TESTS=1`. По умолчанию module-scope fixture создаёт один детерминированный файл размером 1025 МиБ для обоих алгоритмов. Перед записью проверяется свободное место с запасом 256 МиБ. Эталоны `hashlib.sha256` и `hashlib.sha3_256` обновляются теми же блоками во время записи, поэтому отдельный проход по файлу не нужен. Файл удаляется после теста, в том числе при ошибке.

Команда запуска в PowerShell:

```powershell
Remove-Item Env:CRYPTOCORE_LARGE_TEST_MIB -ErrorAction SilentlyContinue
$env:CRYPTOCORE_RUN_LARGE_TESTS="1"
python -m pytest -q -s tests/test_large_file_hash.py -rs
Remove-Item Env:CRYPTOCORE_RUN_LARGE_TESTS -ErrorAction SilentlyContinue
```

До добавления ускорения оценка полного запуска на этой машине составляла около 3,5 часа. Эта оценка относилась к обычному Python и основывалась на замерах 100 МиБ, а не на выполненном прогоне 1025 МиБ.

Механизм теста проверен на файле размером 1 МиБ:

- SHA-256: 5,48 с;
- SHA3-256: 6,95 с;
- итог: `2 passed`.

Этот короткий запуск не закрывает TEST-4.

Проверка TEST-4 завершена в спринте 5 на файле **1025 МиБ = 1 074 790 400 байт**, с установленным extra `speed`:

| Алгоритм | Время, с | Скорость, МиБ/с | Результат |
|---|---:|---:|---|
| SHA-256 | 9,845 | 104,118 | совпал с `hashlib.sha256` |
| SHA3-256 | 12,475 | 82,163 | совпал с `hashlib.sha3_256` |

Итог отдельного запуска: `2 passed in 26.77s`. Это время включает создание файла и эталонов. Пакеты компилятора уже были загружены другими тестами; обработка самих полных блоков выполнялась собственными JIT-раундами. Повторение в полном наборе также прошло: 10,032 с и 13,085 с соответственно. Отличия между запусками отражают текущую нагрузку системы.

## Спринт 5: MAC и ускорение хеширования

### Окружение и способ ускорения

Проверка выполнена 20 ноября 2026 года на Windows, с Python 3.13.12, Numba 0.68.1, NumPy 2.5.5 и llvmlite 0.50.0. Дополнительные пакеты устанавливаются командой:

```powershell
python -m pip install -e ".[dev,speed]"
```

Криптографические операции SHA и HMAC реализованы в проекте. Numba используется только как компилятор собственного кода: расписание слов и 64 раунда SHA-256, а также 24 раунда Keccak-f[1600] записаны явно. `hashlib` и библиотечный `hmac` служат эталонами в тестах и проверяющих скриптах. Для CMAC используется разрешённый заданием существующий примитив AES-128, а конструкция CMAC написана самостоятельно.

Обычный Python сохранён. В обоих вариантах для декодирования слов используется `struct.unpack`; в ускоренном варианте полные блоки передаются одним вызовом в компилируемую функцию. Частично заполненный блок при больших входных частях тоже обрабатывается с ускорением. NumPy получает представление входа через `frombuffer`, без копирования файла; размер рабочих массивов раундов постоянный.

Дисковый кэш Numba содержит скомпилированный код, а не сообщения и ключи. Первый запуск может включать стоимость компиляции. Отсутствие Numba автоматически выбирает обычный Python. Переменная `CRYPTOCORE_PURE_PYTHON=1` принудительно выключает ускорение.

### Корректность MAC и интерфейса

HMAC проверен по [RFC 4231](https://www.rfc-editor.org/rfc/rfc4231.html): случаи 1–4, случаи 6–7 с длинными ключами и первые 128 бит результата для случая 5 с усечением. Сама библиотека и CLI возвращают полный 256-битный MAC. Уточнение к формулировке m5: случаи 1–4 находятся в разделах 4.2–4.5 RFC, а не все в разделе 4.2.

Для ключей проверены длины 0, 1, 16, 32, 63, 64, 65, 100 и 131 байт, для сообщений — пустой ввод и границы padding SHA-256. Потоковые тесты используют части от 1 до 8192 байт и проверяют повторный `digest()` и возможность продолжить `update()` после него.

AES-CMAC проверен по примерам NIST для сообщений длиной 0, 16, 20 и 64 байта из [AES_CMAC.pdf](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Standards-and-Guidelines/documents/examples/AES_CMAC.pdf). Дополнительно проверен 40-байтный вектор, известный по RFC 4493. Сообщения около границ 16-байтного блока сравниваются с независимым CMAC из PyCryptodome.

CLI-тесты покрывают генерацию и проверку сохранённого MAC, stdin, пустые файлы, пути с пробелами, запись LF, ключи разных длин, неверный алгоритм, отсутствующий ключ и конфликтующие аргументы. Изменение одного бита файла или ключа и изменение MAC приводят к отказу. Проверка сравнивает полные значения через `secrets.compare_digest`; отдельный тест запускает настоящий `python -m cryptocore` и проверяет коды завершения.

Ожидаемый MAC разбирается с учётом пробелов, BOM и имени файла. Некорректная длина, неверный hex, несколько записей и слишком большой файл отклоняются. Ошибка чтения посреди сообщения сохраняет существующий файл результата. Тесты чтения запрещают запрос частей больше 8192 байт.

| Требования m5 | Реализация и проверки |
|---|---|
| STR-1–STR-3 | Пакет `cryptocore.mac`, прежние тесты, README, сборка wheel |
| CLI-1–CLI-3 | `dgst --hmac --key`, произвольная длина hex-ключа, вывод с одним пробелом |
| CLI-4, IO-2 | `--verify`, успешная проверка и отказ, гибкий разбор ожидаемого MAC |
| CLI-5, MAC-6, TEST-8 | Бонусный AES-128-CMAC, генерация подключей и векторы NIST |
| MAC-1–MAC-4, TEST-1, TEST-5 | Собственный HMAC на SHA-256, RFC 4231, границы длины ключа |
| MAC-5, IO-1, TEST-7 | Чтение по частям и реальный файл больше лимита памяти процесса |

## Спринт 6: аутентифицированное шифрование

Проверка выполнена 26 ноября 2026 года на Windows с Python 3.13.12, PyCryptodome 3.23.0 и установленным extra `speed` для прежних проверок SHA/HMAC. GCM и GHASH написаны на обычном Python и не используют JIT. Из PyCryptodome рабочий GCM вызывает только AES-128 над одним блоком; готовые GCM и HMAC служат независимыми эталонами в тестах.

### Корректность GCM и Encrypt-then-MAC

- `tests/test_gcm.py` проверяет пять 128-битных тегов из официального [NIST AES_GCM.pdf](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Standards-and-Guidelines/documents/examples/AES_GCM.pdf), примеры AES-128 1–5: пустой ввод, сообщения 64 и 60 байт, AAD 0, 20 и 64 байта. Вектор с 96-битным тегом из примера 6 не используется, поскольку проект требует полный 128-битный тег.
- 378 сочетаний длин nonce (1, 8, 12, 13, 16, 60), сообщений и AAD сравниваются с независимым GCM PyCryptodome. В том числе проверены неполные блоки, пустые поля и обработка нестандартного nonce через GHASH.
- Табличное умножение GHASH сравнивается с битовым алгоритмом 1 из SP 800-38D. Отдельно проверяются продолжение неполного блока между частями потока, разделение AAD/ciphertext, `inc32` при переполнении младшего слова, ограничения длин и запрет продолжения после финализации тега.
- Для небольшого пакета GCM меняется по одному каждый бит nonce, ciphertext и тега. Во всех случаях, а также при неверном AAD и ключе, проверка отказывает. Подмена метода расшифрования тестовой заглушкой доказывает, что открытый текст даже не вычисляется до проверки тега.
- `tests/test_etm.py` независимо собирает AES-CTR и стандартный HMAC-SHA256 и проверяет точный формат MAC. Покрыты пустое сообщение, границы блоков, потоковый AAD, изменение каждого бита пакета и каждой части ключевого материала, усечение пакета и перенос байтов из AAD в ciphertext. IV, длины полей и AES-ключ привязаны к MAC. Проверка выполняется до вызова CTR decrypt.
- По 1000 шифрований одним экземпляром GCM и EncryptThenMAC дали по 1000 уникальных случайных nonce/IV. Это проверка генерации, а не доказательство невозможности повторов.

### CLI, файлы и ошибки

`tests/test_cli_gcm.py` проверяет файл `nonce[12] || ciphertext || tag[16]`, полный цикл, независимое расшифрование PyCryptodome, пустые файлы, размеры вокруг 16 и 8192 байт, пути с пробелами, hex-AAD, бинарный `--aad-file`, автоматические ключи/имена и внешний nonce через `--nonce` и `--iv`. При явном nonce вход содержит только `ciphertext || tag`.

При отказе аутентификации CLI возвращает `1`, не выводит открытый текст, не создаёт выходной файл и сохраняет прежний файл результата. Настоящий запуск `python -m cryptocore` подтверждает код завершения и пустой stdout. Неверный hex, длина nonce и несовместимые аргументы дают `2`.

Проверены короткие чтения, запрет чтения больше 8192 байт, ошибки CSPRNG, отсутствующий файл, ошибка AAD после первой части и ошибка публикации результата. Готовый результат публикуется через атомарную замену, а автоматическое имя защищено от перезаписи при гонке. Для режима exclusive требуется поддержка hard link файловой системой; проверка на Windows выполнена на NTFS. Замена входного файла готовым результатом при явном `--output` также проходит.

Расшифрование использует сохранённую копию ciphertext. Специальный тест изменяет исходный файл после успешной проверки и подтверждает, что результат получается из проверенных байтов. Временные файлы удаляются при обработанных ошибках. Аварийное завершение процесса и восстановление после потери питания не моделировались.

## Спринт 7: получение ключей

Проверка выполнена на Windows с Python 3.13.12, Numba 0.68.1 и прежними зависимостями проекта. Добавлены пакет `cryptocore.kdf`, собственный PBKDF2-HMAC-SHA256, счётчиковая иерархия ключей и CLI `derive`. Рабочая реализация использует собственный HMAC спринта 5. Библиотечные `hashlib.pbkdf2_hmac`, стандартный `hmac` и OpenSSL используются только в тестах и проверяющем скрипте.

### Уточнения к примерам задания

В m7 требуется PBKDF2-HMAC-SHA256, но ожидаемые значения взяты из [RFC 6070](https://www.rfc-editor.org/rfc/rfc6070.html), где PRF — HMAC-SHA1. Для SHA256 эти ответы неверны. Проверка выполнена по двум настоящим векторам PBKDF2-HMAC-SHA256 из [RFC 7914, §11](https://www.rfc-editor.org/rfc/rfc7914.html#section-11): `passwd/salt`, 1 итерация, 64 байта и `Password/NaCl`, 80000 итераций, 64 байта. Дополнительно сохранены входы RFC 6070 с длинными строками и NUL, но ожидаемые SHA256-результаты вычисляются независимым эталоном.

Команды OpenSSL используют явно выбранный `digest:SHA256`, `hexpass:` и `hexsalt:`. Это предотвращает выбор другого PRF и смешение ASCII-соли с бинарной солью. Значения вроде `fixedappsalt` из примеров задания отклоняются как некорректный hex. Модуль `kdf/hkdf.py` следует точной формуле иерархии из задания `HMAC(master_key, UTF8(context) || INT32_BE(counter))`; это не HKDF Extract/Expand из RFC 5869.

### Математическая корректность и совместимость

- `tests/test_pbkdf2.py`: два вектора RFC 7914, фиксированные ответы SHA256 для `password/salt` на 1/2/4096 итераций, все длины ключей 1–100 байт, пустые значения, NUL и Unicode UTF-8. Пароли длиной 0/1/63/64/65/131/4097 и соли длиной 0/1/51/52/55/56/63/64/65/100/4097 проверяют нормализацию ключа HMAC, границы padding SHA и длинный ввод.
- Результаты обычного Python и скомпилированной цепочки сравниваются на 1000 и 1001 итерации, с пустым и длинным паролем, солью на границе padding и выходами 1/33/65 байт. Отдельный тест проверяет 1000000 итераций и 65-байтный результат, то есть три независимые цепочки PBKDF2. Отсутствие Numba моделируется и выбирает собственный HMAC на Python.
- `tests/test_key_hierarchy.py`: точная формула HMAC для длин 1–100, детерминизм, разделение контекстов, пустой/Unicode/NUL-контекст, разные типы бинарного master key и счётчик больше 255. Полученные ключи применены к GCM и Encrypt-then-MAC для полного цикла.
- `tests/test_kdf_openssl.py`: **36 успешных сравнений** с `openssl kdf`: четыре сочетания пароля и соли, включая NUL, длинные бинарные данные и пустые значения, три числа итераций и длины 1/32/65 байт. OpenSSL найден и все случаи выполнены без пропусков.
- Неположительные итерации и длины, `bool`, неверные типы и длина больше `(2^32-1)*32` отклоняются до вычисления или выделения ключевого буфера. Изменения HMAC сохраняют потоковый интерфейс, `compute()`, повторный `digest()` и возможность продолжить `update()`.

### CLI и обработка секретов

Проверены значения по умолчанию `pbkdf2`, 100000 итераций, 32 байта, случайная соль 16 байт, точный stdout `KEY_HEX  SALT_HEX`, явная соль с верхним регистром и пустые пароль/соль. **1000 вызовов CLI** с автоматической солью дали 1000 разных 16-байтных солей. Это проверка генерации, а не математическая гарантия отсутствия повторов.

Все три источника пароля проверены: аргумент UTF-8, точные байты файла и UTF-8 из именованной переменной окружения. Файловый пароль сохраняет NUL и завершающий перевод строки; значение переменной окружения не изменяется. Источники взаимоисключающие, один обязателен.

`--output` содержит ровно бинарные байты ключа, без соли и LF; stdout продолжает содержать ключ и соль для сохранения параметров. Ошибки аргументов возвращают `2`, отсутствующий источник, отказ CSPRNG и ошибка публикации — `1`, успех — `0`. Ошибки сохраняют прежний файл и не выводят ключ. Настоящий запуск `python -m cryptocore derive` проверяет точку входа, stdout и бинарный файл.

Тест удерживает ссылку на переданный в KDF `bytearray` пароля и проверяет, что CLI обнуляет его и после успеха, и после ошибки. Это очистка принадлежащей CLI изменяемой копии, а не обещание стереть неизменяемые строки Python, `argv`, окружение или все состояния HMAC. Ограничение явно описано в README.

### Скорость и повторное использование HMAC

HMAC подготавливает состояния SHA после ipad/opad один раз. Метод `digest_message()` копирует эти состояния и не меняет рабочий поток. Ускоренная ветка PBKDF2 получает состояния и U1 из этого же HMAC, затем компилирует собственные U2..Uc и XOR поверх существующих раундов SHA-256. Ключи и состояния передаются как данные выполнения, а не константы компиляции. При отсутствии Numba или `CRYPTOCORE_PURE_PYTHON=1` сохраняется обычный Python.

Скрипт `scripts/benchmark_kdf.py` использует фиксированные публичные пароль `benchmark-password` и соль `000102030405060708090a0b0c0d0e0f`, ключ 32 байта. Отдельный прогрев на 1000 итераций, включая загрузку компилятора и дискового кэша, занял **1,252 с**. Далее выполнено по одному замеру:

| Итерации | Собственный PBKDF2 с JIT, с | `hashlib` как эталон, с | Совпадение |
|---|---:|---:|---|

Это время внутри уже запущенного процесса после прогрева. Отдельный CLI дополнительно загружает Python и компилятор; первая компиляция нового ядра может занять больше времени. Один замер на точку не является статистическим микробенчмарком. Обычный Python существенно медленнее и не имеет этих показателей.

JSON включает версии Python и Numba, платформу, параметры, прогрев, время каждого замера, результат и подтверждение совпадения с эталоном. Значение по умолчанию 100000 соответствует ТЗ; рекомендации по соли и современному числу итераций приведены отдельно в README.
