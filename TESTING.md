# Проверка CryptoCore

## Проверка генератора через NIST STS

### Зачем

NIST Statistical Test Suite (STS) - набор из 15 статистических тестов.
С помощью него проверялись байты из `cryptocore.csprng.generate_random_bytes`.

Такая проверка помогает найти заметные статистические закономерности в случайных данных, но не доказывает криптографическую стойкость генератора.

### Окружение

- NIST STS 2.1.2;
- WSL 2;
- Ubuntu 24.04.5 LTS;
- исполняемый файл:

```text
/home/nak/nist-sts/sts-2.1.2/sts-2.1.2/assess
```

Отдельной документации README, PDF или DOC в установленной поставке STS не оказалось, поэтому параметры запуска были проверены по исходникам программы, в основном по `src/assess.c` и `src/utilities.c`.

### Данные

Файл со случайными данными создаётся скриптом проекта на Windows вне репозитория:

```powershell
python scripts/generate_sts_data.py C:\Users\nak\cryptocore_sts\cryptocore_sts_data.bin
```

Размер файла:

```text
10 000 000 байт
80 000 000 бит
```

В WSL этот же файл доступен по пути:

```text
/mnt/c/Users/nak/cryptocore_sts/cryptocore_sts_data.bin
```

### Запуск

NIST STS запускался из его корневого каталога:

```bash
./assess 1000000
```

Число `1000000` означает длину одной проверяемой последовательности в битах.

Ответы на вопросы программы:

```text
0
/mnt/c/Users/nak/cryptocore_sts/cryptocore_sts_data.bin
1
0
80
1
```

По порядку это означает:

- читать данные из файла;
- использовать указанный путь;
- выбрать все 15 статистических тестов;
- оставить параметры тестов по умолчанию;
- обработать 80 последовательностей;
- использовать бинарный формат входных данных.

В результате файл размером 80 000 000 бит был разделён на 80 последовательностей по 1 000 000 бит.

Использовались стандартные параметры:

- Block Frequency: `M = 128`;
- Non-overlapping Template: `m = 9`;
- Overlapping Template: `m = 9`;
- Approximate Entropy: `m = 10`;
- Serial: `m = 16`;
- Linear Complexity: `M = 500`.

Перед запуском каталог результатов `experiments/AlgorithmTesting` не содержал старых файлов, поэтому результаты разных запусков не смешивались.

Итоговый отчёт STS находится здесь:

```text
/home/nak/nist-sts/sts-2.1.2/sts-2.1.2/experiments/AlgorithmTesting/finalAnalysisReport.txt
```

Подробные результаты отдельных тестов находятся в каталогах:

```text
experiments/AlgorithmTesting/<TestName>/
```

Файл со случайными данными и полный набор результатов STS в Git не добавляются.

### Как читать итоговый отчёт

В отчёте STS используются два разных показателя.

1. **PROPORTION** показывает, сколько последовательностей прошли конкретный тест.

   Отдельная последовательность считается прошедшей, если её `p-value` не меньше `0.01`.

   В контексте STS ориентир из m3 `p-value >= 0.01` прежде всего относится к этому уровню.

2. **P-VALUE** в итоговом отчёте проверяет, насколько равномерно распределены p-value всех последовательностей.

   Для этого показателя STS использует другой порог:

```text
P-VALUE >= 0.0001
```

Минимальная допустимая доля прошедших последовательностей рассчитывается по формуле NIST SP 800-22:

```text
(0.99 - 3 * sqrt(0.99 * 0.01 / m)) * m
```

Для 80 последовательностей получается примерно:

```text
76.53
```

Для 52 последовательностей:

```text
49.33
```

В STS 2.1.2 рассчитанный порог хранится в переменной типа `int`, поэтому дробная часть отбрасывается. Фактически программа использует значения 76 и 49.

В итоговом отчёте это выглядит так:

```text
The minimum pass rate for each statistical test with the exception of the
random excursion (variant) test is approximately = 76 for a
sample size = 80 binary sequences.

The minimum pass rate for the random excursion (variant) test
is approximately = 49 for a sample size = 52 binary sequences.
```

Если строка не проходит один из критериев STS, программа помечает её символом `*`.

### P-VALUE ниже 0.01

У пяти строк из 188 значение `P-VALUE` оказалось ниже `0.01`.

Это не считается провалом STS, потому что для этого показателя используется порог `0.0001`.

Эти значения приведены отдельно:

- Non-overlapping Template, шаблон 34 (`001001011`): `0.006196`, `80/80`;
- Non-overlapping Template, шаблон 54 (`010000111`): `0.001859`, `79/80`;
- Non-overlapping Template, шаблон 138 (`111101010`): `0.006196`, `79/80`;
- Non-overlapping Template, шаблон 145 (`111111000`): `0.003577`, `77/80`;
- Random Excursions Variant, состояние `+1`: `0.002374`, `51/52`.

Все эти значения выше штатного порога STS `0.0001`.

### Random Excursions

Для Random Excursions и Random Excursions Variant использовались только 52 последовательности из 80.

Эти тесты работают только с последовательностями, в которых набралось достаточное число циклов случайного блуждания.

Для последовательности длиной 1 000 000 бит требуется не меньше 500 циклов. Этому условию соответствовали 52 последовательности.

Оставшиеся 28 последовательностей эти тесты не использовали. Само по себе это не считается отказом теста.

NIST SP 800-22 рекомендует использовать не менее 55 последовательностей для проверки равномерности p-value.

В данном запуске подходящих последовательностей было 52, поэтому значения `P-VALUE` для Random Excursions и Random Excursions Variant нужно оценивать с учётом этого ограничения.

Это относится в том числе к значению:

```text
0.002374
```

для состояния `+1` в Random Excursions Variant.

### Вывод

Все 15 тестов NIST STS были выполнены.

В итоговом отчёте нет строк со звёздочкой `*`, все 188 строк прошли критерии, которые использует STS.

Явных статистических проблем в данных, полученных через `cryptocore.csprng.generate_random_bytes`, тесты не обнаружили.

При этом один прогон NIST STS помогает выявить статистические проблемы, но не доказывает безопасность или криптографическую стойкость CSPRNG.

## Спринт 4: хеширование

### Корректность

SHA-256 и SHA3-256 проверяются по четырём контрольным векторам и известным ответам, используемым в тестах:

| Сообщение | SHA-256 | SHA3-256 |
|---|---|---|
| пустое | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` | `a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a` |
| `abc` | `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` | `3a985da74fe225b2045c172d6bd390bd855f086e3e9d525b46bfe24511431532` |
| `abcdbcdecdefdefgefghfghighijhijkijkljklmklmnlmnomnopnopq` | `248d6a61d20638b8e5c026930c3e6039a33ce45964ff2167f6ecedd419db06c1` | `41c0dba2a9d6240849100376a8235e2c82e1b9998a999e21db32dd97496d3376` |
| миллион символов `a` | `cdc76e5c9914fb9281a1c7e284d73e67f1809a48a497200e046d39ccc7112cd0` | `5c8875ae474a3634ba4fd55ec85bffd661f32aca75c6d699d0cdcb6c115891c1` |

Для SHA-256 отдельно проверяются длины 0, 1, 55, 56, 63, 64, 65, 119, 120 и 128 байт. Для SHA3-256 проверяются длины 0, 1, 134, 135, 136, 137, 271, 272 и 273 байта. Дополнительные детерминированные сообщения сравниваются с `hashlib`.

Потоковый интерфейс проверяется подачей одного сообщения целиком и частями разного размера. Тесты также подтверждают, что внутренний буфер хранит только неполный блок, повторный `digest()` не меняет состояние, а после него можно продолжить `update()`.

Лавинный эффект проверяется на шести заранее заданных сообщениях для обоих алгоритмов. В каждом сообщении меняется младший бит первого байта. Для каждой пары должно измениться строго больше 100 и строго меньше 156 бит результата. Среднее по шести парам должно находиться в диапазоне от 120 до 136 бит.

### Совместимость с внешними утилитами

SHA-256 сравнивался с `sha256sum` из GNU coreutils 8.32, установленным вместе с Git for Windows.

Для SHA3-256 в m4 указана команда `sha3sum -a 256`. В использованном окружении `sha3sum` не найден, поэтому для проверки применялся OpenSSL 3.2.1:

```text
openssl dgst -sha3-256
```

Это отклонение от TEST-3 в m4. OpenSSL выступает независимой реализацией SHA3-256. Если задана переменная `CRYPTOCORE_SHA3SUM` или совместимый `sha3sum` найден в `PATH`, автоматический тест использует `sha3sum`; иначе выбирается OpenSSL.

Проверяются пустой файл, короткий текст, набор всех байтов от `0x00` до `0xff` и детерминированные данные длиной 4097 байт. Из вывода CryptoCore и внешней утилиты извлекается только 64-символьное значение хеша, потому что текстовый формат строк у программ различается.

### Сборка пакета

Wheel собирался из чистой копии, полученной через `git archive HEAD`:

```powershell
python -m pip wheel <копия> --no-deps -w <каталог>
```

Сборка выполнялась с изоляцией. В `.venv` нет `setuptools`, поэтому `pip` установил его во временное окружение сборки. `.venv` и `pyproject.toml` не менялись.

В wheel присутствуют `cryptocore/hash/__init__.py`, `cryptocore/hash/sha256.py`, `cryptocore/hash/sha3_256.py`, `cryptocore/csprng.py` и прежние модули AES, режимов и padding. Точка входа в `entry_points.txt`:

```text
[console_scripts]
cryptocore = cryptocore.cli:main
```

### Скорость

Скрипт `scripts/benchmark_hash.py` сравнивает CLI целиком: `python -m cryptocore dgst` и системная утилита получают один детерминированный файл, после чего значения хешей сверяются. Каждый замер выполнялся один раз. Это практическое сравнение CLI, а не статистический микробенчмарк.

|---|---:|---:|---:|---|---:|---:|
| SHA-256 | 1 | 5.97 | 0.168 | sha256sum | 0.04 | 24.7 |
| SHA3-256 | 1 | 7.97 | 0.125 | openssl | 0.07 | 13.9 |
| SHA-256 | 10 | 55.38 | 0.181 | sha256sum | 0.08 | 119.5 |
| SHA3-256 | 10 | 73.83 | 0.135 | openssl | 0.09 | 110.0 |
| SHA-256 | 100 | 538.86 | 0.186 | sha256sum | 0.51 | 196.0 |
| SHA3-256 | 100 | 695.22 | 0.144 | openssl | 0.47 | 212.9 |

Хеши во всех строках совпали.

На малых размерах результат системных утилит заметно зависит от фиксированных расходов на запуск процесса. Строки для 100 МиБ лучше показывают разницу: CryptoCore медленнее примерно в 1000–1500 раз.

Низкая скорость связана с тем, что раунды SHA-256 и перестановка Keccak-f с битовыми операциями и циклами выполняются интерпретатором Python. Горячие циклы специально не оптимизировались, чтобы код оставался простым для чтения и разбора.

Команда запуска:

```powershell
python scripts/benchmark_hash.py --sizes 1 10 100
```

### Файл больше 1 ГиБ

Тест `tests/test_large_file_hash.py` включается только при `CRYPTOCORE_RUN_LARGE_TESTS=1`. По умолчанию module-scope fixture создаёт один детерминированный файл размером 1025 МиБ для обоих алгоритмов. Перед записью проверяется свободное место с запасом 256 МиБ. Эталоны `hashlib.sha256` и `hashlib.sha3_256` обновляются теми же блоками во время записи, поэтому отдельный проход по файлу не нужен. Файл удаляется после теста, в том числе при ошибке.

Команда запуска в PowerShell:

```powershell
Remove-Item Env:CRYPTOCORE_LARGE_TEST_MIB -ErrorAction SilentlyContinue
$env:CRYPTOCORE_RUN_LARGE_TESTS="1"
python -m pytest -q -s tests/test_large_file_hash.py -rs
Remove-Item Env:CRYPTOCORE_RUN_LARGE_TESTS -ErrorAction SilentlyContinue
```

По замерам на этой машине ожидаемое время полного запуска — около 3,5 часа.

Механизм теста проверен на файле размером 1 МиБ:

- SHA-256: 5,48 с;
- SHA3-256: 6,95 с;
- итог: `2 passed`.

Этот короткий запуск не закрывает TEST-4.
